# Legal notes for independent implementation

This file is general information, not legal advice.

## Why independent implementation matters

Copyright protects source code and other original expression. It generally does not give ownership of every functional idea, method, or interoperability goal. Risk can still come from copyright, patents, trademarks, contracts, access-control laws, or other rules.

A clean-room process is commonly used to separate functional observation from new implementation. A strict process uses one group to create a neutral behavior specification and a separate group to write original code without access to the earlier source.

No process can guarantee that a project will never receive a legal complaint. For commercial release or a serious dispute, ask a qualified lawyer to review the facts.

## Project safeguards

JamScan uses these safeguards:

- Original source code and original protocol identifiers
- No copied source files
- No claim of compatibility with another format
- A written independent-implementation record
- A contribution rule against unlicensed source copying
- A third-party notices file
- Git history and test files that can preserve development evidence

## United States references

- United States Copyright Office, 17 U.S.C. section 1201(f), reverse engineering for interoperability: https://www.copyright.gov/title17/92chap12.html
- Electronic Frontier Foundation, Coders' Rights Project Reverse Engineering FAQ: https://www.eff.org/issues/coders/reverse-engineering-faq

Laws differ by country and can change. License terms, website terms, patents, and trademarks require separate review.
